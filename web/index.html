Send

The box's text is sent. Choosing a file clears it so the file is sent; clear the box yourself to send the file again.

Any file. It is compressed before it is sent, with its name and type.

Encrypts what you send. The phone asks for this password before it shows the message or file.

More

What it protects: the message or file, with its name and type. They are encrypted on this computer with AES-GCM, using a 256 bit key made from the password (PBKDF2 with SHA-256, 200,000 rounds). Nothing goes over the network.

What it does not hide: anyone who films the screen can still see that something is being sent and roughly how large it is.

On the phone: when the transfer completes, the Receive page asks for the password. Enter the same one; a wrong one gives "Wrong password, try again". A lost password cannot be recovered.

Screen settings

Larger blocks read from farther away but carry less per frame.

More

Pros of larger: the phone reads from farther away. Cons: fewer blocks fit on the screen, so each frame carries less.

The cap is the largest block that still fits a grid of 33 by 20 blocks on this screen.

  • Best measured on the test setup (a 4K TV and a phone camera at 1080p): block 28 with the color cube at 2 levels and 10 frames a second, about 26 KB/s.
  • Block 19 failed even on a still frame. At block 16 and below, reads are slow.
  • Aim matters as much as size: center the TV in the camera view and fill about 85 to 90% of its width. Off-center or small aims failed below block 35.
  • Not sure? Run Probe and use the block size the phone recommends.

How a block's color carries bits. More colors carry more but need a clearer view.

More

Bits per block: black and white 1, 4 shades of gray 2, green 4 with red and blue 2 gives 4, and the color cube 3 at 2 levels, 6 at 4 levels.

  • Black and white is the safest at small blocks.
  • Color cube at 2 levels carries more but needs a good aim. It gave the best measured rate, at block 28.
  • Green 4, red and blue 2 failed at every block size.
  • 4 shades of gray failed from block 23 down.

All measured on the test setup (a 4K TV and a phone camera at 1080p).

For the color cube only: 2 levels gives 8 colors, 4 gives 64.

More

Pros of more levels: each doubling adds 3 bits per block. Cons: the colors sit closer together, so the camera confuses them sooner.

  • 2 levels with block 28 was the best measured on the test setup (a 4K TV and a phone camera at 1080p).
  • 256 levels is for saved PNG files only. A camera cannot read it.
  • The other schemes have fixed colors, so this select is off for them.

Phones can join at any time and fill gaps from any frames they read.

More

Pros: at 10 frames a second it finished a 200 KB file in 8.7 s against 18.0 s without it. Cons: it needs about 8% more frames than version 3 for the same file (69 against 64 for a 200 KB file at block 28, cube 2, parity 32 on a 4K screen; computed, not measured), for the packet headers, CRCs and the header copies. At 7.5 frames a second with a clear view the gain was only about 18%, since without it each missed frame comes round again on the next loop. Measured on the test setup.

  • Works well with higher frame rates: it is what makes them pay.
  • Files over 1,024 pieces go out without it. A piece is 214 bytes at block 28, cube 2, parity 32 on a 4K screen (about 219 KB), and the readout shows the limit for the current settings.

Repair bytes in each 255 byte codeword. More repairs more damage but leaves less room for data.

More

Data goes out in codewords of 255 bytes. With parity p, each codeword spends p bytes on repair and can fix up to p / 2 wrong bytes in it. At 32 it fixes up to 16 bad bytes per codeword and spends 32 of each 255 bytes, about 13% of the space.

  • 0 turns repair off: no wrong data byte can be fixed.
  • Stay with 32, the measured setting, unless there is a reason to change.
  • With fountain coding, the frame's payload is split into equal codewords of at most 255 bytes, and each packet carries its codeword length minus parity minus 7 bytes of data: 214 bytes at block 28, cube 2, parity 32 on a 4K screen.

Faster sends more each second but tears more on the phone's rolling shutter.

More

Pros of faster: more frames, so more data, each second. Cons: the phone's camera reads the screen line by line, so a frame change mid-read tears the picture and that read can fail.

  • Fountain coding is what makes the higher rates pay: a torn frame is made up by any later frame instead of waiting a full loop.
  • 10 frames a second with block 28 and the color cube at 2 levels was the best measured on the test setup (a 4K TV and a phone camera at 1080p), about 26 KB/s.

Lower it if the phone shows markers flickering or many CRC failures on a bright screen.

More

The value drawn for full white, from 64 to 255. A lower value dims the whole frame, markers and data alike, so a bright screen does not overexpose the phone's camera. Black stays black.

  • The phone needs no setting: it reads the level steps from a ramp drawn in each frame.
  • Cons: dimming brings the levels closer together. Below 64 they crowd together on a camera.

2Find the best settingsNo network

For a new TV, room or phone. No network needed: the phone measures by light and recommends a block size and colors.

Shows test patterns at each block size, then a frame rate sweep. Bounded by Loops.

How many times Probe runs through every pattern. Until Escape keeps going until you press Escape.

More

Open the Receive page on the phone and aim it first. For each block size from 45 down to 9 (as many as fit this screen), Probe shows a frame that measures the camera, then each color scheme. Then it tries the color cube at 2 levels at several frame rates. The patterns are known, so the phone counts errors against them and shows its recommendation at the end. No network needed.

  • It uses the parity and white level set above.
  • More loops give the phone more reads to judge by, but take longer.
  • Press Escape, or click or tap the screen, to stop early. The phone still recommends from what it saw.

3Development and testingCapture server

Measurement runs we do together. The phone reports results to the computer over the network; payload still goes by light.

Tries settings one after another and sets block size and levels to the best.

Auto tune at each phone camera size, then times a file at several frame rates. Produces a report.

More

Both need the project server started with capture on, and the Receive page open on the phone.

  • Auto tune asks the phone for its 1080p camera, then shows color cube trial frames at 2 and 4 levels one after another. The phone reports each trial's results to the server. At the end it sets block size and levels, and the scheme to color cube, from the best result. Stopped early, it changes nothing.
  • Run tests does this for the phone's 1080p camera and then its 4K camera: switches the camera, runs Auto tune, then times a file of several frames at a series of frame rates. The report table below lists, per camera, the size it delivered, the time per read, the levels found, the best setting and the bytes per second at each rate. It does not change your settings.
  • If a frame cannot hold the test data, the status says so; choose less parity and try again.
